# Security and privacy: current routine release

Checked October 3, 2026 against the source, the live Firebase deployment, and the App Check API for project `asmr-skin-coach` (project number `756603780588`). The app currently uses Firebase email/password sign-in and requires a verified email before paid access. Face scanning, AI coaching, photo journals, and affiliate offers are disabled in the deployed callable Functions and release navigation.

The live project-level Auth configuration has email/password enabled, requires a password, and has a verification-email template. Both registered iOS and Android apps use this project. A server-side password policy now enforces an eight-character minimum for new or changed passwords without forcing existing users to upgrade on sign-in. A live seven-character REST signup was rejected with `PASSWORD_DOES_NOT_MEET_REQUIREMENTS` on October 3. The mobile source accepts any nonempty password on sign-in so older valid accounts are not locked out by the new-account rule. [Google documents the policy enforcement options](https://docs.cloud.google.com/identity-platform/docs/password-policy).

## Server authorization

- `verifySubscriptionAccess` checks the Firebase caller and verified email, then queries RevenueCat's server API. Its response and the Firestore entitlement cache come from that server check, never a client-reported purchase. The deployed Function atomically limits callers to 12 verification requests per account per 60-second window in `usage/{uid}` before making the vendor request. The deletion guard is read in the same transaction so a stale token cannot recreate usage after cleanup. RevenueCat webhooks are not subject to this user-facing limit. Its boundary and concurrency behavior passed unit tests; a signed-device live burst test remains open.
- The deployed RevenueCat verifier accepts only the four current Apple/Play annual and monthly product identifiers with a finite active expiration or vendor-reported grace period, and denies refunded purchases. It handles a coexisting Test Store lifetime projection by checking the approved subscription records. The live Firestore rules require `isPro=true` and a future timestamp expiry for paid reads and writes. The deployed rule text was read back after rollout, and the Test webhook returned 401 without its bearer token and 200 with it. A read-only scan of five entitlement documents found no Pro document with a null expiry. The same verifier, run read-only against the existing live Pro subscriber, returned an active approved monthly subscription with finite expiry. Purchase, restore, refund, grace, and account-switch behavior still need signed-device QA.
- The deployed callable Functions set `enforceAppCheck: true` for subscription verification, account deletion, and the disabled scan/coach/affiliate endpoints. Signed physical-device token behavior still needs verification before public release.
- Firestore rules bind user data to `request.auth.uid`, require a server-written unexpired Pro entitlement for paid collections, and deny client entitlement writes. Profile creation and updates both reject the same 11 server-owned fields, including tier, credits, scan allowance, roles, and deletion status; the Firestore emulator tests each field on both paths. This tighter rule was deployed on October 3, 2026. Cloud Storage rules deny private uploads and reads; only catalog art is public.
- Account deletion uses a callable Function to remove the configured Storage prefixes, recursively delete the user document tree and legacy root records, then delete the Firebase Auth user. Direct client deletion of the parent profile is denied because Firestore does not cascade subcollections. The deployed service first creates `accountDeletionGuards/{uid}` **without an expiry**, marks the profile as deleting, and revokes its paid entitlement in one transaction, before Storage cleanup. This blocks stale-token writes and delayed webhook writes even if Storage cleanup fails. Only after all data cleanup does the guard enter `awaiting-auth`; only after Auth confirms the user is absent does it receive an `expireAt` two hours later. Phase changes are transactional and cannot be regressed by a concurrent retry. A scheduled Function rechecks `awaiting-auth` guards if the last write fails, but never expires a guard for an existing Auth user or incomplete cleanup. Failed deletions while Auth still exists need a caller retry or support follow-up.
- Firebase Auth also permits a signed-in user to delete their Auth record directly, bypassing the app's callable. The deployed retry-enabled first-generation Auth `onDelete` trigger calls the same idempotent cleanup service for this path. It checks that the Auth account is absent before any write; a delayed event does nothing if that UID already belongs to a newer account. After installing the guard and before destructive cleanup, it checks again. If an account reappears in that interval, cleanup stops and the guard remains without a TTL for support review. The trigger never calls Admin `deleteUser()` for an already deleted event. Its event is asynchronous, so there can be a brief interval before it installs the guard; a failed event must be monitored and retried. Admin bulk `deleteUsers()` does not emit per-user deletion events and must not be used without a separate cleanup process. Disposable live accounts deleted through the Firebase Auth REST API on October 3, 2026 triggered cleanup of their profiles, nested routines, root entitlement and usage records, and Storage objects. The trigger completed successfully before and after the lockfile deployment; each guard reached `completed` with an `expireAt` about two hours later. The callable path and simultaneous live deletion race still need signed-device tests.
- The deployed callable rejects account deletion when the caller's verified ID token has a missing, future-dated, or more than five-minute-old `auth_time`, before cleanup begins. This closes the recent-login gap created by Admin SDK deletion, which does not ask for the user's password. The mobile app prompts for the account password, reauthenticates with Firebase, and refreshes the token before calling deletion. The current private TestFlight build 10 and Play internal code 11 include this change; signed-device end-to-end behavior still needs testing.
- Account deletion can recursively remove many Firestore and Storage records. On October 3, the generation 2 callable limit was raised from 60 to 300 seconds, matching the Auth deletion trigger; the live Function was read back as `ACTIVE` with `timeoutSeconds=300`. TestFlight build 10 and Play internal code 11 wait 330 seconds so the app can receive the server's result. This path still needs a signed-device end-to-end test.
- The guard's `expireAt` Firestore TTL policy is **ACTIVE**, and the scheduled finalizer's `state` + `nextCheckAt` composite index is **READY**. Its absent `expireAt` disables expiration while deletion is incomplete. [Firestore says TTL cleanup is asynchronous and typically occurs within 24 hours after expiry](https://firebase.google.com/docs/firestore/ttl). The [Cloud Scheduler](https://firebase.google.com/docs/functions/schedule-functions) API is enabled, the job is **ENABLED**, and the finalizer Function is **ACTIVE**. A manual trigger logged `finalized: 0, retained: 0, failed: 0` at 22:02 UTC on October 3, 2026. Recovery with a real pending guard and end-to-end account deletion remain unverified.

## App Check: verified live configuration

The Android app has a registered Play Integrity configuration. The iOS app has registered App Attest and DeviceCheck configurations. Each reports a 3,600-second App Check token TTL. The mobile source initializes those providers for release builds.

The Firebase App Check service API currently reports **`UNENFORCED`** for Cloud Firestore, Cloud Storage, Firebase Authentication, and OAuth2. Registration and a signed build do not establish enforcement for those services. The signed TestFlight and Play internal-test builds still need physical-device token and billing checks. [Firebase's enforcement guide](https://firebase.google.com/docs/app-check/enable-enforcement) states that enabling a service rejects unverified requests and may take up to 15 minutes to apply.

## Release gate

1. Prove on final signed physical iPhone and Android builds that App Attest/DeviceCheck and Play Integrity tokens reach the callable membership verifier, and that account creation, email verification, paid Firestore reads/writes, restore, and deletion work. Inspect [App Check request metrics](https://firebase.google.com/docs/app-check/monitor-metrics) for both platforms and legitimate traffic.
2. The recent-login check, verification limiter, and Auth deletion trigger are deployed. A disposable direct Firebase Auth deletion invoked cleanup and left a completed two-hour guard. Confirm on a signed-device build that an old session cannot call deletion and fresh password reauthentication can. After callable deletion, deliver a delayed RevenueCat account webhook and confirm no user tree or entitlement is recreated. Confirm an incomplete guard stays unexpired, a cleanup-complete guard is finalized after Auth deletion, and the active TTL policy eventually removes it. Check the scheduled Function logs during recovery.
3. Once signed-device traffic is verified, enable App Check enforcement for Cloud Firestore and Cloud Storage in Firebase, then repeat both-device flows and monitor rejected requests. Assess Authentication and OAuth2 enforcement separately against provider requirements and sign-in flows. Record the exact live modes after rollout. Do not treat callable `enforceAppCheck` as Firestore/Storage enforcement.

## Secrets and operational limits

RevenueCat server credentials are Firebase Function secrets (`REVENUECAT_SECRET_API_KEY`, `REVENUECAT_WEBHOOK_TOKEN`); the mobile app contains only RevenueCat's public platform keys and Firebase client configuration. The webhook authenticates its bearer token and reconciles current subscriber state with RevenueCat. The disabled scan and coach Functions explicitly declare empty secret bindings; their live Function configurations have no Gemini key attached. Keep server secrets out of the client and logs.

GitHub secret scanning found two Google API keys in the checked-in iOS and Android Firebase configuration files. Both are Firebase client identifiers, which [Firebase documents as public by design](https://firebase.google.com/docs/projects/api-keys). The Google Cloud API Keys API shows each key has the Firebase-provisioned API allowlist and neither can call the Generative Language API; the separate Gemini key is not in this repository. Both alerts were resolved as intentional public client configuration with that rationale, and the open alert count was read back as zero. The app's data still depends on Auth, Security Rules, and App Check; the latter's service-level enforcement remains a release gate. Do not tighten production client restrictions without testing the signed apps first.

The historical local Android signing backup no longer contains release password literals in its Gradle file. Its passwords are in the owner's macOS Keychain and its Gradle file and keystore are owner-only (`0600`). This backup is outside Git; the registered Play upload certificate is unchanged. See [operations.md](operations.md) for the local recovery identifiers.

The live RevenueCat `TEST` webhook returned 401 without the configured bearer token and 200 with it. This checks endpoint authentication only; a delayed account event after deletion has not been tested. The public Firebase Hosting legal pages are live.

The deployed Functions package includes a standalone `packages/backend/package-lock.json`. The October 3 generation 2 Cloud Build log confirms `npm ci` from that lock; the generation 1 Auth trigger build ran `npm install` with the same lock included in its source ZIP. CI repacks the shared library, checks its tarball against the committed copy, and audits a clean backend production install from the lock. That install resolves the patched Express/body-parser/`qs` chain to 4.22.3/1.20.8/6.16.0 and reports zero high or critical findings. Nine moderate audit entries remain through `firebase-admin` 13's older Google Cloud libraries, all traced to the `uuid` buffer-bounds advisory; the installed Google clients call `uuid.v4()` without a caller-provided buffer, outside the advisory's affected API methods (`v3`, `v5`, `v6`). Upgrade Admin and its transitive dependencies in a separate compatibility change. The old scan state machine is dormant; its unit tests do not prove production App Check, atomic quotas, or scan safety.

The root workspace audit also reports inherited Expo, Metro, and React Native findings. We traced the direct advisories before considering upgrades. `braces` and `node-forge` are reached by local bundling and certificate tooling, with no patched upstream release in the installed chains. The older `@grpc/grpc-js` copy comes through the Firebase Web SDK; this app does not run the server-side mutual-TLS configuration in its advisory, and the deployed Admin SDK path has a patched copy. The `decode-uri-component` dependency is used by Expo Router's query serialization; its active native link parser uses `URL.searchParams`, and no reachable vulnerable parsing path was found. A forced audit fix would cross Expo SDK compatibility boundaries or downgrade key packages. Continue tracking upstream fixes and rerun the audit during supported SDK upgrades; these findings are not proof that the app is invulnerable.
